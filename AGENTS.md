# Kingfisher AI Coding Agent Instructions

## Project Overview

Kingfisher is a deterministic spectral element radiation transport code built on
[MFEM](https://github.com/mfem/mfem). It is written in C++20.

- **C++ sources** are in `src/`, public headers in `include/`, and GoogleTest
  unit tests in `tests/`.
- **Dependencies** all come from [CPM](https://github.com/cpm-cmake/CPM.cmake)
  in `cmake/Dependencies.cmake`: fmt, rapidyaml (input files are YAML),
  GoogleTest, and MFEM v4.10. No system packages are needed beyond a compiler,
  CMake ≥ 3.25, and Ninja.
- **Documentation** is Sphinx (MyST Markdown) in `docs/source/`, with the C++
  API reference generated by Doxygen and Breathe. The theory pages are in
  `docs/source/theory/`.
- **Python** is planned but not present yet: a Python API that generates YAML
  input files, similar to how OpenMC's Python API generates XML.
- **MPI** is planned but not implemented. `NOTE(parallel)` comments in the
  CMake files mark where it will hook in. Changes should not make that harder,
  for example by adding global state that assumes a single process.

## Build and Test

Everything goes through the CMake workflow presets in `CMakePresets.json`:

```bash
cmake --workflow --preset debug     # configure, build, and test (Debug)
cmake --workflow --preset dev       # configure, build, and test (RelWithDebInfo)
cmake --workflow --preset release   # optimized executable, no tests
cmake --workflow --preset docs      # documentation only (see docs/environment.yml)

# After the first build:
cmake --build --preset dev && ctest --preset dev
ctest --preset dev -R <regex>       # run a subset of tests
```

Set `CPM_SOURCE_CACHE` (for example to `~/.cache/CPM`) so that build
directories share one copy of MFEM instead of downloading it for each preset.

Test files are `tests/*_test.cc`. They are picked up automatically by the glob
in `tests/CMakeLists.txt`.

## Git Workflow

- `main` is the integration branch. Pull requests target `main`.
- Create a feature branch off `main`, open a PR, and fill in
  `.github/pull_request_template.md`.
- CI runs the build and tests (`ci.yml`), clang-format and clang-tidy checks
  (`format-check.yml`), the docs build (`docs.yml`), and an automatic Claude
  review (`claude-code-review.yml`).

## Conventions

The full style guide is `docs/source/developer-guide/style.md`. In short:

### C++: Google C++ Style Guide

| Kind | Convention | Example |
|---|---|---|
| Types (classes, structs, enums, aliases) | `PascalCase` | `AngularQuadrature` |
| Functions and methods | `PascalCase` | `ComputeScalarFlux()` |
| Accessors and mutators (optional) | `snake_case` | `num_groups()`, `set_num_groups()` |
| Variables and parameters | `snake_case` | `num_groups` |
| Class data members | `snake_case_` | `angular_flux_` |
| Struct data members | `snake_case` | `weights` |
| Constants (`constexpr`, including local) and enumerators | `kPascalCase` | `kMaxOrder`, `kVacuum` |
| Local non-`constexpr` `const` variables | `snake_case` | `num_dofs` |
| Namespaces | `snake_case` | `kingfisher::transport` |
| Macros | `KINGFISHER_UPPER_CASE` | `KINGFISHER_USE_MPI` |
| Files | `snake_case.cc`, `.h` | `sweep_operator.cc` |

- Formatting is `.clang-format` (Google base style), checked in CI with
  clang-format 18.
- Naming and common bug and performance problems are checked by `.clang-tidy`,
  run in CI with clang-tidy 18.
- Header guards are `KINGFISHER_<PATH>_<FILE>_H_`.
- Public APIs have Doxygen comments.

### Data-oriented design

Kingfisher's hot loops (angular sweeps, element assembly, source and group
iterations) touch large amounts of data per step, so the data layout matters
more than the class hierarchy:

- Store hot data as **structure of arrays** in contiguous buffers (for example
  `mfem::Vector`, `mfem::Array`, or a flat buffer indexed by group, angle, and
  element), not as a container of per-element or per-angle objects.
- **No heap allocation, virtual calls, or `std::function` calls inside hot
  loops.** Allocate workspaces once, outside the loop.
- Loop order should follow memory order.
- Plain structs plus free functions that act on them are preferred over deep
  class hierarchies.
- Keep MFEM's memory model (`Read()`, `Write()`, `ReadWrite()`, `mfem::forall`)
  usable, so that GPU execution remains possible.

### Testing

New functionality must be tested. See "What must be tested" in

When Python is added: PEP 8, numpydoc docstrings, type hints, `pathlib.Path`
